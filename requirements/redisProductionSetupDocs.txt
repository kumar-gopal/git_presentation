
## 1) Connection & topology

**Definition:** How your app connects to Redis and what Redis deployment you run (single instance, Sentinel HA, Cluster).
**Why:** Proper topology ensures high availability, failover, and partition tolerance.
**Example:** Production = Redis Cluster (sharding + HA) or Sentinel-backed primary-replica for smaller scale.
**Code hint:**

```js
// use ioredis with sentinels or cluster
const Redis = require("ioredis");
const client = new Redis.Cluster([{ host: 'r1', port: 6379}, ...], { redisOptions: { password: process.env.REDIS_PASSWORD }});
```

---

## 2) Connection pooling & singletons

**Definition:** Use a single shared Redis connection per process (or dedicated pools) rather than creating one per operation.
**Why:** Prevents connection explosion; efficient reuse; required by BullMQ.
**Example:** One `config/redis.js` exported and reused across modules.
**Code hint:** export a singleton client and import everywhere.

---

## 3) Namespacing & key design

**Definition:** Consistent key naming convention (entity:version:id, env:service:entity:id).
**Why:** Prevents collisions, enables targeted invalidation, eases debugging.
**Example:** `product:v3:12345`, `tenant:acme:cart:5678`, `bull:email:repeatable`.
**Rule:** Use lowercase, short prefixes, avoid special characters.

---

## 4) Cache versioning & invalidation strategies

**Definition:** Methods to invalidate stale cache — versioning, TTLs, explicit delete, change streams.
**Why:** Avoid stale reads; efficient invalidation at scale.
**Example:** `version:product = 4` → keys `product:v4:id`. Bump version on updates.
**Code hint:** store `version:<entity>` and `INCR` on update.

---

## 5) Cache get/set/del helpers (centralized)

**Definition:** One utility module that handles JSON serialization, TTL defaults, error-safe operations.
**Why:** Uniform behavior, single place to change TTL or serialization, graceful failures.
**Example:** `cache.get(key)`, `cache.set(key, value, ttl)`, `cache.del(key)`, `cache.flushPattern(pattern)`.
**Code hint:**

```js
await redis.set(key, JSON.stringify(value), 'EX', ttl);
const v = JSON.parse(await redis.get(key));
```

---

## 6) TTL strategy & eviction policies

**Definition:** Assign sensible TTLs per resource type; configure Redis eviction policy.
**Why:** Control memory usage; avoid memory spikes; ensure fresh data.
**Examples:**

* product detail: 10–30 min
* product list/search: 1–5 min
* session tokens: 30 days
  Set Redis `maxmemory-policy` e.g., `volatile-lru` or `allkeys-lru` depending on persistence needs.

---

## 7) Cache warming & background refresh

**Definition:** Proactively populate or refresh cache (e.g., after deployment or heavy invalidation).
**Why:** Reduce first-request latency after invalidation/version bump.
**Example:** Background job to pre-warm top 1k product pages using BullMQ.

---

## 8) Auto-invalidation from DB (Change Streams / Model hooks)

**Definition:** Invalidate cache automatically when DB records change using Mongoose model hooks or MongoDB Change Streams.
**Why:** Strong consistency between DB and cache.
**Example:** `User.watch().on('change', ...)` → bump version or delete cache keys.

---

## 9) Pub/Sub (cross-instance invalidation)

**Definition:** Publish invalidation events so multiple app instances (or services) clear local caches.
**Why:** Multi-instance setup needs distributed invalidation in real-time.
**Example:** Publish `invalidate:product:123` and have all instances subscribe.

---

## 10) Separate Redis DBs / logical separation

**Definition:** Use separate Redis logical DBs or separate clusters for caching vs queues (BullMQ).
**Why:** Prevent queue pressure from evicting cached data; isolate workloads.
**Recommendation:** Use separate Redis databases or dedicated Redis clusters for BullMQ and caching. If using same cluster, namespace keys and set different eviction/config profiles.

---

## 11) Persistence & durability choices

**Definition:** RDB snapshots, AOF, or both.
**Why:** Balance durability vs performance; queues often require persistence.
**Guidance:** Use AOF (append-only) for durability if losing data is unacceptable. For ephemeral caches, persistence is less critical.

---

## 12) Security (ACLs, TLS, auth)

**Definition:** Use Redis AUTH, TLS, and ACLs to secure connections.
**Why:** Protect sensitive data and avoid unauthorized access.
**Example:** cloud providers: use TLS endpoints + ACL users per role.

---

## 13) Monitoring & observability

**Definition:** Collect Redis metrics (hit/miss ratio, memory usage, evictions, latency).
**Why:** Detect cache inefficiencies, memory pressure, and regressions.
**Tools:** Prometheus + Redis exporter, Datadog, NewRelic. Track:

* cache_hits, cache_misses
* evicted_keys
* memory_used, memory_peak
* connected_clients, blocked_clients

---

## 14) Logging & tracing

**Definition:** Log cache events (set/get/miss/invalidate) at debug level; correlation IDs for tracing.
**Why:** Troubleshoot cache correctness and performance issues.
**Example:** use Winston to log `cache miss` for critical endpoints only to avoid noise.

---

## 15) Rate limiting & token buckets

**Definition:** Use Redis to implement distributed rate limiters (leaky bucket / token bucket).
**Why:** Protect APIs, prevent abuse, guard background systems.
**Tools:** Implement with Lua scripts or libraries (rate-limiter-flexible).

---

## 16) Distributed locking

**Definition:** Use Redlock (or equivalent) for distributed locks (inventory decrement, critical sections).
**Why:** Prevent race conditions when multiple instances update same resource.
**Caveat:** Understand Redlock safety model; use for meta-locking, not perfect consensus.

---

## 17) Atomic operations & Lua scripting

**Definition:** Use Redis atomic ops and Lua scripts when multiple ops must be atomic (e.g., conditional set-and-incr).
**Why:** Avoid round-trip race conditions.
**Example:** Use a Lua script to check stock then decrement and set a cache snapshot.

---

## 18) Bulk operations & scan safely

**Definition:** Use `SCAN` with streams to delete patterns safely, avoid `KEYS`.
**Why:** `KEYS` blocks Redis and is unsafe in production.
**Example:** `scanStream({ match: 'product:v*: *' })` then `del` in batches.

---

## 19) BullMQ & queue co-existence

**Definition:** Ensure queues (BullMQ) use separate Redis namespace/db or separate connection with proper backpressure.
**Why:** Jobs and cache should not compete for memory and latency.
**Advice:**

* Use Redis DB index `db=1` for queues and `db=0` for cache.
* Or use separate Redis cluster/node for critical queues.
  **Code hint:**

```js
const queue = new Queue('email', { connection: { host, port, db: 1 }});
```

---

## 20) Fail-open & graceful degradation

**Definition:** If Redis is down, the app falls back to DB reads and continues to function.
**Why:** Avoid full outage because of cache failure.
**Implementation:** Cache helpers return `null` on Redis errors and app reads DB as fallback. Log Redis outages with alerts.

---

## 21) Capacity planning & sizing

**Definition:** Estimate memory needs using dataset size, object size, overhead, eviction.
**Why:** Avoid OOM and LRU thrashing.
**How:** Profile average object size, number of keys, factor in overhead (≈ 2x), provision memory with headroom.

---

## 22) Backup & disaster recovery

**Definition:** Regular backups (RDB snapshots and/or AOF backups) and tested restore plan.
**Why:** Recover from data corruption or accidental deletion.
**Note:** For cache-only data, backup is less critical; for queues and session stores, it's essential.

---

## 23) HA & failover (Sentinel / Cluster)

**Definition:** Configure Sentinel for failover or use Cluster for sharding + HA.
**Why:** Keep system available during node failures.
**Testing:** Perform failover drills and measure RTO/RPO.

---

## 24) Multi-tenant considerations

**Definition:** Support tenants by namespacing keys (`tenant:<id>:product:<id>`) or using separate caches.
**Why:** Prevent tenant data leak and allow per-tenant cache lifecycles and quotas.

---

## 25) Metrics & SLOs

**Definition:** Define cache hit-rate SLOs and alerting (e.g., hit-rate < 70% triggers investigation).
**Why:** Ensure caching actually improves performance.
**Metrics to track:** hit_rate, miss_rate, avg_latency_ms, eviction_rate, memory_usage.

---

## 26) Access patterns & cardinality analysis

**Definition:** Analyze which keys are hot and which are cold; tailor TTLs accordingly.
**Why:** Optimal TTLs and cache warming reduce cache churn and memory pressure.
**Tooling:** Logs, sampling, Prometheus histogram of key access.

---

## 27) Canary & rollout strategies

**Definition:** Gradually enable caching for endpoints (canary) and monitor effects before wide rollout.
**Why:** Reduce risk of cascading failures.

---

## 28) Testing & chaos engineering

**Definition:** Simulate Redis outages, evictions, and latency to verify fail-open behavior and correctness.
**Why:** Ensure robust behavior under real-world failure scenarios.

---

## 29) Security & compliance

**Definition:** Ensure sensitive data is not cached, or encrypt cached payloads.
**Why:** Prevent data leaks and compliance violations (PII).
**Rule:** Avoid caching tokens, passwords, or unmasked PII unless encrypted.

---

## 30) Operational runbook

**Definition:** Document runbook for common Redis operational tasks: failover, reconfigure, upgrade, memory pressure response.
**Why:** On-call engineers need fast, tested steps during incidents.

## Short examples (practical snippets)

### central cache helper (safe)

```js
// cacheClient.js
const redis = require('../config/redis');
const logger = require('../libs/logger');

async function get(key){ 
  try { const v = await redis.get(key); return v ? JSON.parse(v) : null; }
  catch(e){ logger.error('redis get', e); return null; }
}
async function set(key, val, ttl=300){ 
  try { await redis.set(key, JSON.stringify(val), 'EX', ttl); } catch(e){ logger.error('redis set', e); }
}
async function del(key){ try { await redis.del(key); } catch(e){ logger.error('redis del', e); } }

module.exports = { get, set, del };
```

### versioned key & bump (on DB change)

```js
// cacheVersionManager.js
async function buildKey(entity, id){
  const v = await redis.get(`version:${entity}`) || '1';
  return `${entity}:v${v}:${id}`;
}
async function bump(entity){ await redis.incr(`version:${entity}`); }
```

### using with BullMQ (separate DB)

```js
const { Queue } = require('bullmq');
const connection = new IORedis({ host, port, db: 1 }); // DB 1 for queues
const emailQueue = new Queue('email', { connection });
```

## Final operational notes (short)

* **Do not** mix heavy queue workload and cache on the same tiny Redis instance. Use separate DB or cluster.
* **Always** instrument Redis — if hit_rate drops or evictions spike, you must react.
* **Automate** version bump or model hooks for cache invalidation — human-driven invalidation scales poorly.
* **Test** fail-open behavior: bring Redis down in staging and ensure app still answers (with higher latency).
